# Phase 10B 相鄰節點預取與後端切換

前版基準為 `ffef21c`。本版沿用 [Phase 10A 的量測方法](phase10a-interaction.md)，增加首次往同一方向走六格的測試。

## 渲染與記憶體

- GPU 畫面提交後，依最近一次物距變動的方向預備相鄰一格。前景與預取共用光學影像選擇、取樣和工作集檢查。只有所需背景已駐留、光學層全部下載並通過數值驗證、紋理已上傳，首次造訪才直接提交。若預備期間方向、場景或後端改變，前景取得優先權。與前景相同的下載可以共用。背景不相容或單件估計解碼超過 2 MiB 的節點走正常前景流程。
- 活躍後端的光學層上限為 14 MiB。暫停的後端最多保留最近一幀合計 2 MiB 的光學層，超出上限便整組釋放，兩邊合計上限為 16 MiB。GPU 也可保留該幀的背景紋理，計入既有 7 MiB 背景快取。網格切換可重用一張最近的中間紋理，額外上限為 1 MiB。顯示標籤隨完成提交的畫面更新，滑桿即時回應輸入。

## 桌面重播

Chrome 156，390×844 CSS px，DPR 3。首次造訪每步間隔至少 80 ms，讓前景完成後有機會預取。時間從合成輸入到診斷資料更新，真機的觸控、合成及螢幕呈現延遲需另測。

| 情境 | 10A 中位／p95（ms） | 10B 中位／p95（ms） |
| --- | ---: | ---: |
| 40 cm 單眼，首次走 2.6–3.1 D | 9.5／11.4 | 0.4／0.8 |
| 40 cm 雙眼，首次走 2.6–3.1 D | 17.5／404.8 | 0.7／1.1 |
| 40 cm 單眼，已暖機反覆換格 | 8.3／9.0 | 8.0／8.8 |
| 40 cm 雙眼，已暖機反覆換格 | 7.8／8.5 | 8.3／8.9 |
| 20 cm Vivity，1.7／1.8 D 往返 | 15.5／32.3 | 4.5／7.8 |

40 cm 的首次走格，單眼和雙眼各 6 筆全部命中已預取的 GPU 幀。雙眼基準的 p95 是 6 筆中最慢的一筆。20 cm 的 5 筆 GPU 返回全部命中暖路徑，兩端已打包光學層合計最高 2,440,800 bytes。100 cm 的兩處暖網格邊界，JS 提交中位數分別由 0.8 降至 0.5 ms、0.7 降至 0.4 ms。8 ms 的暖幀快速輸入測試各組均提交最後節點，最後輸入到提交的 p95 約 10 ms。

60 項回歸測試通過。Chrome 顯示讀回確認首次預取幀與 Phase 10A 的前景幀逐位元組相同。Chrome 與 Playwright WebKit 的九組獨立 Python WebGL2 案例，差異均在 1 個 sRGB byte 內。刻意延後下一格光學資產，再快速反向，畫面與物距標籤最後均停在最新節點。

```sh
node tests/benchmark-interaction.mjs <Phase-10A-URL> <Phase-10B-URL>
```

手機以 GPU 驗收頁選 Physics-based (OPTrace PSF)。在 40 cm 從 2.5 D 逐格靠近後快速反向，觀察首訪與物距標籤。在 20 cm 將卡寬設為 270 px，選 Vivity-like 單眼往返 1.7／1.8 D，比較第二次開始的切換。

## 資產格式試驗

三張光學樣本用 Pillow 無損重壓 PNG，檔案大小相同。無損 WebP 小約 33–35%，在 Chrome 與 Playwright WebKit 的 RGBA 雜湊皆相同，Chrome 的解碼加畫布讀回中位數則增加約 0.1–1.1 ms。背景的有損 WebP／AVIF 從 988 kB 降到約 534／509 kB，但解碼後與現有背景有像素差異。背景無損 WebP 為 2,231 kB。手機驗收版使用原有格式，光學 WebP 可在 iPhone 真機的冷快取與較慢網路上再比較端到端收益。
